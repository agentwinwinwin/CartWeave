# CJ 订单需求选品 v4

本页描述保留兼容的 `product.opportunity@4.0.0`；新建 CJ 流程默认使用含刊登关注度的 [v5](cj-listing-opportunity.md)，不覆盖旧冻结版本。v4 沿用只读 `POST /product/productDetail/query`，读取 `orderCount`。CJ 文档将其描述为商品 SPU 的订单数，但没有声明统计周期、国家或销售件数；界面、证据与审批不得把它叫作近 90 天销量。`listed` 仍只是刊登次数。[官方文档](https://developers.cjdropshipping.com/en/api/api2/api/product.html)

## 配置与执行

- 按当前工作流目标店铺和团队，使用私有商品简报中的 `cj_pid` 排除已上架或提交结果待确认的商品，不按标题猜同款；在读取订单数前跳过，不占需求达标候选名额。最终交付候选与发送发布前重新核对，发送前在店铺行锁内核对并建立发布意图，避免两轮同时选到同一 CJ 商品。未发布草稿不封锁商品；不同店铺独立，只有已确认下架才能解除排除，超时/待确认下架仍排除。独立供货研究没有店铺上下文，不冒充已执行店铺去重。排除原因和 PID 保存到本轮采集结果，进度显示跳过数量；不删除商品、历史发布证据或批准。

- 新保存的 CJ v4 默认启用 `demandFirstCollection=true` 与 `batchPublishing=true`：第一步分别定义需求门槛、最终合格目标和可调扫描预算 `scanBudget`（默认1000，20–10000）。单关键词批次逐页读取订单证据、按页需求排序后研究；库存、配送或成本不合格继续补位，至少一个完整合格规格才占一款名额。达到合格目标停止，不先扫完整预算；不足时继续翻页直到预算到达或 CJ 分页结束，二者分别提示，不把预算用尽说成全目录无货。历史缺预算版本沿用 `min(500,max(20,limit*5))`，历史多类目仍均分、不转移空缺额度。重复 PID 只读取一次订单证据，每次 worker 只读一页目录或一件订单证据；游标与排除原因持久化，接口失败不当作零结果。一小时内订单证据复用，不刷新时间冒充新证据。旧冻结版本不迁移，编辑稿保存重新冻结才生效。两轮批次审批与逐款发布详见 `cj-launch-runtime.md`。

- 任务使用目录候选，不使用 CJ 热门榜；在本次限额采集范围内读取详情并按订单数降序排序，不宣称全目录销量榜。
- `minimumCJOrderCount` 默认 1；用户可调整门槛，不需要手填实际订单数。缺失保持未知，0 是已知零订单；二者不混同、不用刊登数或 `soldOut` 补造订单数。
- 需求评分权重 45%，成本 35%，总时效 15%，库存缓冲 5%；工厂供货扣分。需求按本批次最大订单数归一化，不能跨任务视为绝对市场评分。建议售价继承系统费用、税费预留与贡献率核算，不预测销售或利润。
- 缺失或低于门槛的候选不进入库存、运费研究；若全部不合格则暂停并保留逐商品原因。订单数达标仍需库存、物流、价格、内容及两轮审核检查。
- 原 v3 的代码、登记版本与冻结运行保持不变。按本次用户要求，编辑中的 CJ v3 标准草稿移除旧 90 天门槛，绑定已注册 v4；必须保存并重新冻结。继续旧运行仍使用旧版本，不能在执行中偷换算法。

## 验证范围

回归使用模拟 CJ 回包（`soldOut=null`、`orderCount=224`），完成十五步选品、审批、测试站发布与可售查询；另验证空值、零值、非法类型和订单数优先排序。测试不是向用户店铺发布商品，也不能保证任意真实目录批次都有合格候选。真实读取仍依赖 CJ 返回数据。
