# 通用工作流前后端契约草案

## 第一阶段实现状态

Django + DRF 第一阶段后端已建立，独立入口为 `/workflow/live`，实际范围见 `backend-phase-one-spec.md`。它从手动提供的 ProductBrief@1 开始，只执行已注册的七步测试站发布主线；并未实现本文全部 CJ、广告、订单、售后与自由图规划。现有 `/workflow/builder` 仍是本地草稿及模拟，不自动把导出的 v2 文档当成后端可执行版本。下文“未来接口”保持完整系统规划的含义。

## 一次接入，多动作复用（接入草稿 v0.1）

`environment.storeIntegration` 保存 channel/name/version/actions/status=draft，`storeRef` 保存连接记录引用。节点通过 `resolveNodeConnection` 继承店铺能力，不将引用复制到各节点；单节点显式覆盖仍优先。广告、CJ、采购、仓库及售后执行等未纳入店铺范围，必须独立确认服务来源。旧文档未声明接入包时仍可进行原有设计演示，不代表已连接。

接入生成 Skill 与日常策略 Skill 分层：前者一次开发多个 API 能力；后者负责分析或生成内容。窗口导出动作契约草案供开发使用，缺失 Schema 不得推断字段或声称验收。当前仅保存单流程设计引用；未来连接目录由服务端持久化并在多个流程引用，不保存凭证到流程文档。

未来后端必须将连接、版本、action ID 映射到已注册且验收的运行适配器，不能只凭前端 Skill ID、能力声明或 approved 字段执行。适配器仍需逐动作确认权限、输入输出、业务语义、幂等、审计及事件来源；生成代码、部署成功和真实验收分别记录。自定义渠道缺少适配实现时禁止借用其他渠道接口。

当前 `lib/workflow/universal.ts` 是跨境电商通用的纯前端设计模型。Amazon 与 Shopify 只是首批示例适配，产品并不限于这两个渠道。没有调用现有 Python 服务，也没有执行入口引用。`frontend-preview` 只表示静态预检，不能标为 Pydantic 验证、真实运行或平台授权。

## 三层边界

平台差异接口现已开放运营 Skill 配置，不再仅藏在技术视图。接入实现可换，系统资格、授权与预算仍固定。所有五条流程的分类和未实现事项见 `workflow-skill-audit.md`；接口步骤保留 `structuralEditing: false`，不因可换 Skill 而允许跳过业务职责。

业务节点固定职责、输入输出版本和允许副作用。Skill 是实现清单，支持 script、connector、llm、media、composite、manual；生成脚本时可以用模型，执行该脚本时不一定使用模型。CJ 来源采集已改为固定系统动作；分析和内容策略可替换，系统校验、计算和授权核心固定。渠道选择替换默认适配绑定，不复制业务图，也不覆盖自选 Skill、节点标题、参数和图编辑。

## 运营编辑边界

`operator-policy.ts` 声明 fixed（系统固定）、parameters（仅开放参数）、skill（可换策略）。画布展示业务动作和产出，权限使用图标、文字与色调共同表达，运行状态不改变编辑权限。固定步骤没有运营删除、重排或替换入口；费用率、市场、核算币种、人工清单等仅按白名单保存。选品、内容、推广素材和经营/售后建议可绑定兼容策略；CJ 采集、资料检查、规则筛选、配送核验、核算和审核不能替换实现。

技术视图用于对接设计，不是管理员认证。内置系统核心只接受受信 core 实现，前端预检拒绝同输入输出的自建替代；渠道适配器在运营窗口可选 Skill、配置连接引用及打开自建清单，技术细节展示契约和执行入口，但清单仍未注册、未授权、未执行。实际后端接入时，必须返回并强制受信节点策略和字段白名单，独立核验可选步骤、身份、渠道能力、授权版本及条件分支。不得信任客户端的标识、按钮状态、技术视图或导出文档中的权限声明。

通用契约保留事实来源、时间、币种、订单状态、履约责任和证据引用。Raw 响应不必进入每条边，可保存为可选 rawRef。相同 JSON 形状不能证明事实相同；Amazon Pending 不能映射成已付款，提交回执不能映射成已可售。

选品链的数量边界明确为：`ProductRecords.records[] → ProductFacts.products[] → SelectionContext.items[]`，同一 requestId 下成本节点为每个规范化候选保留 product 与 calculation。缺失报价的候选仍保留，并标记 insufficient_inputs，不静默丢弃。选品实现比较该批候选，第一版只输出一个 ProductDecision，productId 必须引用本批候选；后续审批、内容和上市只处理该对象。review/reject 不代表允许上市；无合格候选需停止或待复核，不伪造一个商品。多商品并行上市需要未来显式拆分任务能力，当前不隐含循环或批量发布。示例契约展示形状，跨节点候选引用、数量保持及事实条件仍由未来后端校验。

节点效果区分 read、artifact、remote_write、spend、message。FBA 消费订单的履约节点只绑定 read 实现；补货另建任务。自由绑定的 Skill 清单不能授予自身权限，模型和脚本输出 approved=true 不能代替受信审批记录。

## 文档与编辑

### 当前选品到上线主线（替代早期 SelectionContext → ProductDecision 顺序）

前两步任务和 CJ 采集保持不变；原始字段可在 `ProductRecords@1.records[].rawCJ` 或 `source.rawRef` 保留，后端同轮任务上下文继续随数据传递。随后按 `CJProductFacts@1 → EligibleCandidates@1 → DeliveryCandidates@1 → SelectionProposal@1 → SelectionAssessment@1 → ApprovedProductBrief@2 → ListingDraft@1 → ValidatedListing@1 → ApprovedListing@1 → PublicationReceipt@1 → PublishedProduct@1` 推进。上述 Schema 和示例只用于对接设计，未运行结构或语义校验。

`CJProductFacts` 保留变体、原报价币种、仓库国家、库存验证状态、近 90 天销量及未知字段。缺失销量/库存不设为零；销量口径尚未确认时保留 `cj_scope_unconfirmed`。筛选输出合格、待复核、排除三类引用；无合格候选时停止或人工复核，不伪造后续结果。配送使用变体/数量/出发地/目的地估算；这是当前独立站供货配送的初版边界，平台履约和入仓补货的物流成本不能复用为消费者包裹报价，后端 spec 需按履约责任定义。未知税费和不可用线路不得当作零成本或可配送。

策略先建议商品、规格与售价，系统随后按该建议计算广告前贡献空间，费用率是经营假设而非已接入平台费率，需后端店铺配置核实。缺运费、适用税费、有效售价或汇率来源时标记 `insufficient_inputs`。未知广告成本不输出已验证净利润。`review/reject`、未通过供货配送检查或核算不完整不能自动获得上市批准；这些条件需由后端执行，不是当前前端静态预检的能力。

第一轮确认绑定商品、规格、售价、市场和已核验配送报价；第二轮在内容制作和渠道检查之后，人工批准最终草稿，绑定不可变 revision、digest 和审批记录。内容/价格/承诺修改后旧批准失效，必须重走检查和审核；发布需要两轮授权和渠道检查职责。返工从最终审核回到内容制作，不重复发布。当前只实现前端流程设计与明确的模拟审批，不调用 CJ 或发布接口，不覆盖已有浏览器草稿。旧图不自动迁移，导出保留后重新建立模板。

WorkflowDocument schemaVersion=2 包含环境、节点实例、绑定版本、主路径及反馈/协作关系、自建 Skill 清单。模板仅提供起点，预检不要求保留模板节点 ID；存在发布、付款等动作时，依据动作需要检查前置职责。初版编辑器只支持单主路径，不声称支持并行 DAG。

修改后增加 revision 并使旧预检失效。自建入口 entrypointRef 只作展示与将来注册引用；禁止 eval、动态脚本加载或从浏览器直接传 shell 命令。浏览器保存和导出不是后端注册或云端存储。

## 未来接口（本次未实现）

- POST /workflow-definitions/validate：接收完整文档；服务端重新解析受信节点/Skill注册表，Pydantic验证参数及版本化字段，检查能力和图语义。返回 BackendValidationResponse，包含 documentDigest、revision、validationId。前端预检结果不得作为服务端信任凭证。
- POST /workflow-runs：接收 RunRequest，绑定不可变文档版本、真实连接环境、验证票据和幂等键；服务端重新核验账户权限和动作授权。
- GET /workflow-runs/:id/events：SSE 或等价事件流返回 RunEvent。按 sequence 去重与恢复，只有真实事件令等待节点继续。
- POST /workflow-runs/:id/approvals：受信身份批准具体操作、对象、版本、金额范围和有效期。授权记录由服务端生成，Skill不可伪造。
- POST /skills/registrations：提交清单及产物哈希，后端审查入口、依赖、网络/文件/工具权限后注册不可变版本。自建清单在前端显示不代表注册成功。

运行器在每个节点前后验证业务数据，独立核验事实来源、新鲜度和平台实时状态；保存输入输出引用、产生的资产、外部操作 ID 与审计记录。反馈修订不能撤销已执行副作用。只读协作不重跑前驱；等待、审批和运行需要不同事件状态。

真实脚本需受限运行环境、明确允许的能力、超时、资源限额和产物存储。凭证通过连接引用在后端注入，不放入文档、localStorage或导出 JSON。图验证、代码安全、平台授权和执行事实是四个独立判断。

连接引用是逻辑标识，不是凭证。当前引用没有适用渠道元数据，所以跨渠道切换清空 storeRef 和所有节点 connectionRef，要求重新选择账号；自选实现、共用配置与业务参数保留，不会静默改绑。未来连接注册表具备适用范围后，才可选择性保留通用供应 ERP 等连接。后端必须重新验证连接归属、渠道、租户和权限，不能凭引用名称使用账号。

## 可扩展销售渠道

`lib/workflow/channels.ts` 定义 SalesChannelDefinition：稳定 id、显示名称、渠道类型、支持的履约责任、默认履约方式、设计能力声明与适配状态。新增渠道是登记元数据，不是创建账号连接，也不表示已经实现平台 API。供应商、仓库和平台履约是独立的责任维度，不能依据渠道名称猜测履约方式。

WorkflowDocument v2 增加可选 `customChannels`，旧文档没有这个字段仍可导入。浏览器渠道目录使用独立存储键 `commerceos.sales-channels.v1`，添加后本地保存，流程 JSON 同时携带其设计定义。当前目录不是全用户、跨设备共享注册表；后端接入时需增加租户范围、受信渠道/适配器版本、连接资源和目录注册权限。相同平台的多店铺通过独立连接标识区分，不应将账号密钥放入渠道定义。

Skill 的 `channels: ["*"]` 表示实现与渠道无关，仍须符合节点契约、履约范围及能力限制；具体渠道适配器声明注册 ID。新渠道保留业务图和通用核心实现，需要渠道接口的节点默认留空，不借用已有平台适配器。用户可以绑定通用采集脚本或创建兼容实现清单；缺少实现或能力不符时预检不能通过。新增清单及 `read / remote_write / spend / message` 能力声明都不是实际授权，未来后端必须根据真实适配器和账号权限重新核验。

渠道字段的 Schema 改为注册 ID 字符串，而非 Shopify/Amazon 枚举；是否已注册由注册表校验承担。平台负责履约时，消费订单节点只允许只读观察，不允许商家重复采购、出库或通知，该约束适用于所有渠道。

本轮只实现渠道目录的扩展与前端配置，不声称已补齐取消、部分履约、资金子步骤、刊登操作模式或入仓补货等上一轮审查指出的业务缺口。

## 字段 Schema 草案

`lib/workflow/contract-schemas.ts` 提供 13 份可序列化 JSON Schema（Draft 2020-12）与字段示例，可在节点的“输入输出”窗口查看和下载。范围以商品采集、规范化、成本、决策、商品内容、素材、发布结果和订单上下文为主；其余广告、履约、售后契约当前只有名称与版本，需要后续补全字段，不能作为完整运行时 API 使用。

规范化输出保留供应报价与独立市场观察；缺失事实保持 null。图片请求 ImageBrief 不含已生成资产，MediaAsset 才交付产物引用。PublicationReceipt 只声明提交结果，PublishedProduct 需要真实渠道确认。`flow.end` 透传实际前序产物，因此在选品建议处结束仍交付 ProductDecision，不会变成已经可售的商品。

这些草案并未挂接校验器。后端可将它们映射成 Pydantic 模型或用 JSON Schema 校验，但还须核验金额、来源、状态转换与授权等语义。节点运行状态来自未来 RunEvent，浏览器动画不代表脚本或模型已经执行。
# CJ 商品采集的已确认业务边界

商品来源固定为 CJ，不随销售渠道或履约方式变化。`product.collect` 是系统动作而非运营可插拔 Skill；`product.collect.core` 只是当前通用文档模型内的执行描述，未来映射到后端内置 handler，不执行用户上传脚本。当前未实现采集服务。

第一步保持现有参数。后端从第一步真实输出 `ProductQuery@1` 读取 `requestId`、`market`、`category`、`limit`、`requestedCurrency` 及系统解析的来源连接引用；第二步不保存覆盖这些值的参数。前端 `productCollectionTaskParameters` 只展示现有配置，不能替代后端校验的任务对象。后端需要把本轮任务上下文与 `ProductRecords@1` 同时传给下游，保证市场和核算币种不会丢失。

市场、类目、数量如何映射 CJ 查询条件由后端明确实现；不能直接把目标销售国家当成库存所在国家。核算币种属于任务上下文，不代表 CJ 会自动返回该币种报价。保留原始报价币种、字段缺失和采集证据，真实换算属于后续核算。CJ 接口授权、限流、分页、重试、销量口径及具体返回字段在后端 spec 阶段确认，本次不实现。

旧草稿的 CJ 脚本、ERP 或自建采集绑定不会被静默改成已接入 CJ，预检应拒绝。用户需保留旧文件并重新建立当前模板，前端不能把完成引导或预检通过标记为连接成功。
