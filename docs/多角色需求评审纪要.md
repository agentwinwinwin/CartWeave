# Atelier Flow 多角色需求评审纪要

> 日期：2026-09-29  
> 参与视角：B2B SaaS 产品经理、美国服装独立站卖家/运营、自动化系统技术架构负责人、主设计整合

## 1. 各角色的核心判断

### 产品经理

- 原 P0 同时包含画布、问答、异常、审批、商品、发货与凭据，范围相当于多个产品，缺少一条可验证的黄金路径。
- 审批不是异常；商品生命周期、库存和健康状态不能混成一条状态链。
- 先验证 CJ 候选到 Shopify 上架可以降低风险，但该阶段不能称为业务闭环。
- 应用可演示、可试运营、可经营三个交付等级替代含糊的“MVP”。

### 卖家/运营

- 日常第一优先不是聊天或昨日 GMV，而是已付款未履约、缺货、成本突涨、物流逾期、退款、同步失败和待审批金额。
- 服装经营必须以 Variant、仓库、运费、时效和客户承诺为单位，Product 级建模不足以防止发错尺码或卖出不可履约商品。
- 可以暂缓自动 CJ 下单，但不能暂缓订单可见性、人工履约接管、库存/成本守门和快速隐藏。
- 没有订单、采购、履约、售后与利润账本，就不能称为经营中枢。

### 技术架构

- Inngest 函数不能随在线工作流动态注册；正确做法是发布不可变 ExecutionPlan，由固定 dispatcher/executor 解释。
- “Run + Node + 执行序号”不是可靠幂等键。外部动作要使用稳定 EffectLedger，并承认跨系统只能通过本地记账、供应商幂等和对账实现确定结果。
- 外部调用超时可能是“已成功但回执丢失”，必须进入 UNKNOWN 并先对账。
- 上架和履约应是两个连续工程里程碑。前者验证引擎和可补偿外部写入，后者验证资金、PII、扣款和不可逆履约。

## 2. 主要分歧与对话结果

### 分歧一：首版只做上架，还是同时做履约

产品经理最初建议先完成“候选 → 利润 → 文案 → 审批 → Shopify 上架”，卖家指出这会产生真实订单却没有承接能力。技术架构认为两条高风险写链路一次上线会使故障定位困难。

最终决策：

- 工程上分成连续的 M1 与 M2，不绑成一次验收。
- M1 完成可靠上架，同时上线订单只读接入、Variant 唯一映射、人工履约待办、库存/成本守门和快速隐藏。
- M2 才开放经执行前审批的 CJ 采购与物流回写。
- 只有 M2 完成，才可声明“电商闭环跑通”；只有售后与利润对账完成，才称“经营中枢首版”。

### 分歧二：审批是否属于异常

原方案为了统一入口，将 WAITING_APPROVAL 定义为 warning 异常。三方一致认为这会污染异常率、健康度和 SLA。

最终决策：Approval、Incident、HumanTask 分开存储和统计，只在 Action Inbox 中聚合展示。全局栏分别显示“阻塞异常”和“待审批”。

### 分歧三：自动化等级是否使用 L0/L1/L2

卖家指出邮件、CJ 扣款和发货通常不可撤回；架构负责人指出补偿能力依动作类型而异。

最终决策：使用 `REVIEW_BEFORE_EXECUTE`、`EXECUTE_AND_NOTIFY`、`AUTONOMOUS`，并由每个动作声明可用策略、金额与影响范围上限、数据新鲜度、批次、熔断和补偿能力。

### 分歧四：首页以问答还是运营队列为中心

保留“问答与行动中心”作为默认入口，但第一屏先展示按资金、履约、SLA、审批和同步健康排序的行动队列。确定性概览和异常处理不依赖 LLM；聊天输入位于行动信息之后。

## 3. 最终冻结的产品边界

M1：一个真实商品从 CJ 数据到 Shopify 上架，全程可审批、可回放、可撤下、无重复副作用；真实订单只读可见并可人工接管。

M2：一个真实 Shopify 测试订单经执行前审批创建唯一 CJ 采购单并回写物流；回执丢失、重放、缺货和取消竞态都有确定处理结果。

Operating Release：复杂履约、售后和 append-only 利润账本完成，达到覆盖率、自动处理率和对账闸门。

自由连线、任意第三方 Skill、模板交易市场、多租户 UI、计费、开放式写入问答、完整移动端和深色模式均后置。
