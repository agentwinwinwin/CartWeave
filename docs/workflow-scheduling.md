# 业务定时器

入口 `/schedules`，工作流页也有“定时运行”入口。先在工作流保存并校验冻结，再创建计划、选择冻结版本和时区，设置每天、每周或每隔 1–720 小时执行。创建默认暂停，用户显式启用后从下一个计划时间开始，不立即运行。界面能编辑、启停、查看触发记录，并返回原运行画布查看进度和审批。

## 执行与边界

计划仅绑定不可变 DesignRelease，不读取最新草稿。当前支持完整 CJ 选品到测试站主线；七步发布模板缺少每轮的真实商品输入，不能作为循环合成商品任务。其他业务模板未实现调度执行，不标为可运行。

`WorkflowSchedule` 保存配置与下次触发，`ScheduleOccurrence` 保存原计划版本、触发时间和关联 WorkflowRun。服务端调用同一个 `start_run`，不创建第二套业务执行器。每次重新检查操作者权限、店铺版本、CJ 连接和审核过的 Skill；审批开关和强制审批规则沿用冻结流程。不会自动批准、采购、付款或投广告。

默认策略：

- 上一轮排队、执行、待审批、待渠道回执或需要处理时，本时段记录 skipped；其他 CJ 选品占用也跳过，不积压。
- 关机、休眠或服务停止导致晚于计划时间超过 90 秒时，记录 missed，并计算未来时段，不补跑多轮。
- 启动业务检查失败记录 blocked，暂停计划；修复配置后显式重新启用。
- 暂停只停止未来触发，不取消既有运行。取消和断点恢复在原运行页进行。
- 每日/每周使用 IANA 时区；夏令时跳过不存在的当地时刻，重复当地时刻仅触发一次。间隔从保存/启用或本次触发时刻往后计算，不按历史欠账补跑。

## 接口与运行

`GET /api/v1/schedules`：当前团队计划、可选冻结版本、调度心跳；`POST` 创建；`PATCH /{id}` 修改并要求 expected_revision。读操作要求团队成员，写操作要求 operator/admin；计划不接受凭证或执行脚本。触发历史按时间保留，页面展示最近十次，不提供破坏性删除。

新增迁移：`COMMERCE_ENV=local ../server/.venv/bin/python manage.py migrate`（backend 目录）。本机原 `npm run desktop` 的 runworker 每 5 秒调用调度；生产原 Celery Beat 的 `apps.runtime.tasks.dispatch` 使用相同服务，无新增 Redis 之外的调度依赖。关闭浏览器不影响；关闭后端或电脑不会运行，不能唤醒电脑。

团队锁 → 计划行锁 → 触发唯一约束，与 start_run 的幂等键和事务 Outbox 配合。多调度器不会为同一时段生成两次运行；SQLite 仍只用单 worker，生产并发和未来 MySQL 验收另做，不因定时模块增开 worker。

回归测试 `manage.py test tests.test_schedules` 使用临时测试数据库和模拟 CJ，覆盖全十五步两轮审批、触发幂等、时区/DST、错过时段、忙碌跳过、版本不随草稿变化、权限与 Skill 失效、暂停及乐观锁，不调用真实资金或物流接口。
