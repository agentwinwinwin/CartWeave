# CJ 自动选品证据

> 本文记录历史 v3 的近 90 天销量策略。当前默认已按用户要求切换到 [CJ 订单需求选品 v4](cj-order-count-selection.md)，使用 `orderCount`，不把订单数冒充近 90 天销量；已冻结 v3 运行不迁移。

在定义商品任务点击“配置 CJ 自动证据并绑定选品算法”，同时配置 `marketEvidenceSource=cj`、`minimumCJSales90d`（缺省 1）与审核登记的 `product.opportunity@3.0.0`。保留原类目、关键词、国家、店铺及其他业务参数，移除互斥的外部证据引用。需保存新设计；不改变已冻结运行。

## 来源与真实验证

- 复用已有加密 CJ 连接；不新增密钥、不将凭证放入草稿。
- `POST /product/productDetail/query` 是只读查询，按官方文档读取确切大小写 `id`、`soldOut`（近 90 天销量）和 `listed`（刊登数）。[官方商品文档](https://developers.cjdropshipping.com/en/api/api2/api/product.html)
- 2026-10-03 使用现有本机连接做了一件只读样本验证：接口返回相同 PID，`soldOut=null`、`listed=13`、`orderCount=0`。这证明接口可访问，不证明任意商品一定有销量或能真实跑通发布。不会把 orderCount、listed 或库存当作 soldOut 的替代。
- CJ 文档未在该字段声明目标国家分布、上一周期、搜索量、获客成本或竞品售价。90 天销量不得折算冒充两个 30 天窗口或国家销量；刊登次数不得称为真实竞争商家数量。

## 执行

试搜保留原 CJ 类目、关键词、数量，额外只读核验前三件商品，显示空字段与未研究数量。每轮最多三次额外详情请求。完整工作流由 worker 在商品资料节点逐件读取任务上限内的销量；未知、零或低于门槛的商品不进入库存和配送核验。全部不合格时停在资料节点并保留原因，不用模型补事实，不扩大范围。

通过配送核验后，v3 按本批最大销量归一化需求分、最低到货成本归一化成本分、最短总时效归一化履约分、50 件饱和库存缓冲评分：销量 45%、成本 35%、时效 15%、库存 5%；工厂供货扣 10。权重为首版可审查规则，不是训练或验证过的预测模型。广告成本与竞争售价未知，建议价仍为广告前核算价，不保证盈利或市场接受度。

来源、输入和提案输出用 Pydantic 检查；报价和销量证据一小时过期。批准摘要绑定提案，日常执行重核 Skill 审核状态、证据时间和提案。强制两轮人工核验，即使普通审核开关关闭或方案转至旧七步入口。明确重试会重新读取同一批商品，不只改时间戳。不会采购、付款或投广告。

原 v1 供货算法、v2 外部市场证据算法保留，不覆盖审核过的代码；扩展目标市场研究仍可选择第三方来源，但不作为 CJ 基础选品的必填配置。

本机安装新版本：`COMMERCE_ENV=local COMMERCE_DESKTOP=1 ../server/.venv/bin/python manage.py register_opportunity_skill --cj`。只安装受信函数，不执行模型生成或上传脚本。

## 目录采集与真实销量排序

新任务与恢复的编辑稿统一使用 `candidateSource=catalog`，不使用热门 `productFlag=0`，界面不再提供热门选项。旧冻结版本的 trending 执行保留兼容，不修改在途运行。类目、关键词、总额度与库存过滤照常保留；不会为得到结果自动扩宽范围。CJ 未提供全目录销量排序字段，本系统只在限额候选内排序。

运行顺序是目录候选采集 → 逐件读取商品事实与近 90 天销量 → 在 `selection.sales_ranking` 保存销量降序（并列按 PID，未知在末尾并明确不合格）→ 按此顺序做 SKU 库存与配送核验 → v3 综合评分与售价核算 → 审批 → 内容与渠道检查 → 准备发布数据 → 发布与可售确认。已审核评分代码不改：销量 45%、到货成本 35%、时效 15%、库存 5%；综合评分不等于纯销量排名。销量来自真实回包，缺失不填零、不用 orderCount 或刊登数代替，全部缺失会暂停。编辑稿保存并冻结新版本后生效，旧版本不改。

依据：[CJ 官方商品接口文档](https://developers.cjdropshipping.com/en/api/api2/api/product.html)。
