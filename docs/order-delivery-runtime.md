# 订单到交付：本地测试闭环

## 实现范围

订单模块从同一店铺接口包同步订单与独立包裹事实，展示承运方、运单、状态与事件时间。订单支付/履约与包裹运输是不同状态，未知不是未发货，更不能当签收。

标准八步在原画布保存、冻结、运行、停止与恢复：读取订单 → 核验履约条件 → 确认方案 → 创建测试发货单 → 等待出库 → 店铺回写 → 等待交付 → 归档。配置归首节点 runtime，绑定订单 UUID 和明确测试授权；当前仅 test-store / merchant，本机桌面模式，不执行供应商采购付款或平台履约。

创建与回查使用原运行 SHA256 操作键，服务端在发送前持久化 ExternalOperation。未知结果只回查原键：已创建则恢复同一运单，未查到也不自动重发。人工确认核对同一订单版本/付款/规格数量。一个订单只创建一个发货单；跨店铺和冲突输入拒绝。等待节点每15秒读取原包裹，不因时间或动画推进。

测试站联调中心显式推进 prepared → dispatched → in_transit → delivered，运输中也可进入 exception。物流异常停下，不能标完成。签收写入订单的新版本，并保留三条轨迹；没有实际实体发货、签收人或承运商。测试执行不扣减库存，不能作为生产库存预留策略。

## 一次接入、完整下载

`test-store.v1@1.5.0` 的核心 actions 增加 order.detail / fulfillment.create / fulfillment.lookup / shipment.read / fulfillment.record / shipments.read。旧发布1.3描述及1.3、1.4冻结版本兼容不变；新能力需明确重新验收，不隐式扩权。

下载包内 extensions 完整列出原 test-store.testing@1.0.0（测试订单、客服上下文/回复/回查、素材归档/回查）及 test-store.events@1.0.0（有序消息页、显式物流事件）。原测试扩展Schema与摘要不变，新有序页和物流事件保持独立路径。只有明确联调验收后使用测试扩展。

新映射会话一次展开核心与扩展全部26项动作，按动作分别检查请求/响应字段路径、依据与缺口。旧会话契约快照不重写；规则更新并不表示已调用模型重新映射或注册其他渠道。下载的生成API规则和映射规则说明所有相关业务动作、来源与幂等边界。生产供应商、广告、付款、邮件、自动经营调整明确未支持。

## 操作

1. 在配置店铺接入重新验收1.5接口包并保存；联调中心确认启用测试扩展。
2. 联调中心创建测试购买，打开订单到交付，选择订单并确认测试执行器。
3. 保存、校验并冻结、运行。在确认履约权限处明确批准。
4. 联调中心读取记录，分别点击模拟已出库、运输中、签收。流程等待来源事件继续。
5. 订单模块点击同步，读取订单和物流各一页；点击订单查看轨迹。需要完整大批数据时继续同步，页面刷新不是远端同步。

测试使用临时数据库和实际本机 HTTP，不使用用户订单，不涉及真实付款。多包裹字段设计可展示多个来源包裹，但本次测试执行仅支持一个订单的一张测试发货单；拆单/部分履约/真实地址/成本/库存预留需另行设计验收，不能宣称已支持。
