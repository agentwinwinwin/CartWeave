# Atelier Flow 电商自动化中枢：业务逻辑优化稿 v2.0

> 日期：2026-09-29  
> 文档定位：业务规则与范围的事实源，供产品、设计、研发和验收共同使用  
> 输入来源：原《电商自动化中枢-业务设计移交文档》及产品经理、独立站卖家、技术架构负责人三方交叉评审  
> 适用范围：Atelier Nine，美国市场，Shopify + CJ Dropshipping，单店、美元、自营试运行

## 1. 本版直接修正的关键问题

1. 不再把“选品到上架”称为完整 MVP。交付分为可演示、可试运营、可经营三个等级，只有订单、采购、履约、售后和利润对账闭环后，才称为“电商自动化中枢首版”。
2. 审批与异常是两种实体。两者共用“需要处理”收件箱和卡片容器，但状态机、角标、SLA 和统计分开。
3. 商品阶段、渠道发布状态、变体库存和业务健康度拆成正交状态，不再把“库存告警”当商品生命周期阶段。
4. 自动化等级改成动作策略与风险护栏。系统不再承诺发货、调价、群发邮件“可撤回”。
5. 工作流发布生成不可变 `ExecutionPlan`，由固定 Inngest 执行器解释运行；不动态注册或编译 Inngest 函数。
6. 外部动作采用稳定 `effect_key`、效果账本和对账机制。超时后的未知结果不得直接重试。
7. 首发上架能力必须同时提供订单只读接入、Variant 唯一映射、人工履约接管、库存/成本守门和快速隐藏，避免自动上架制造无人承接的订单。
8. 问答不是写库捷径。它只能查询确定性数据或生成结构化命令草稿，所有写操作复用正常的校验、审批、幂等和审计链路。

## 2. 产品目标与成功定义

产品要帮助卖家完成两件事：减少重复运营工作，同时确保任何资金、库存、客户承诺和外部写操作都可追溯、可拦截、可人工接管。

首阶段不以“节点数量”或“自动化数量”衡量价值，使用以下指标：

- 上架准备耗时、人工修改率、重复发布数。
- 已付款订单进入待办的延迟、最老未处理订单时长。
- 变体映射准确率、库存与成本数据新鲜度。
- 外部动作重复副作用数，目标始终为 0。
- 异常发现时间、人工接管时间、逐项恢复成功率。
- 预估贡献毛利与已实现贡献毛利的覆盖率及对账差异。

## 3. 交付等级与上线闸门

### 3.1 可演示版本 Demo

范围：CJ 候选导入 → 去重 → 确定性利润预估 → LLM 文案 → 人工审批 → Shopify 沙箱或草稿上架；展示流程运行、商品时间线、异常和审批。

限制：不可承接真实订单，所有外部写操作只进入沙箱或 Shopify draft。

闸门：

- 同一链路可反复运行，重试不产生重复商品或 Variant。
- 工作流版本、节点、Skill、Prompt、Schema 与输入输出均可追溯。
- 凭据和个人信息不进入日志、提示词或执行回放。
- 模拟“外部成功但响应丢失”时先对账，不重复执行。

### 3.2 可试运营版本 Pilot

范围：允许少量真实商品与订单。首批采用“上架自动化 + 人工履约交接”，随后开启单供应商、单仓且固定 `REVIEW_BEFORE_EXECUTE` 的自动采购试点。

首发同期必须具备：

- Shopify 订单只读接入，至少同步 paid、cancelled、refunded、订单行、Variant、金额和时间。
- Shopify Variant 与 CJ Variant 的唯一映射；保存尺码、颜色、仓库、成本、库存、运费、预计时效及采集时间。无法唯一映射不得发布。
- 新付费订单在 5 分钟内进入人工履约待办，包含截止时间、负责人、CJ 下单所需数据、人工处理记录以及 CJ 单号与 tracking 回填。
- 上架前即时复查库存、成本、运费、时效和利润；上线后定时同步。数据过期、缺货或利润跌破阈值时关闸并生成待办。
- 一键将受影响商品或 Variant 转为 Shopify draft/hidden，并保留审计。
- 页面显示配送时效和退换/取消政策；取消和退款状态在系统内可见。

试点限制：单店、美国、美元、单 CJ 供应商、单仓、白名单不超过 10 个商品或 30 个 Variant、所有采购与发货均为执行前审批、无批量发布。

闸门：先完成连续 7 天且至少 20 次无错发布，以及前 5 个真实订单“捕获 → 人工 CJ 下单 → tracking 回填”演练；自动采购扩大试点前，再满足连续 14 天或累计 100 单、零重复采购/发货、逐单可恢复、收入/货品/运费/退款对账差异不超过 1%。

### 3.3 可经营版本 Operating Release

范围：订单拆单/合单、多包裹、部分缺货、取消、退货退款、补发、物流异常、库存回写全部进入状态机；利润账本覆盖收入、折扣、税、支付费、货品、运费、广告分摊、退款、重发和拒付。

闸门：

- 连续 30 天覆盖目标店铺至少 95% 的订单。
- 自动处理成功率至少 95%，其余全部进入可操作队列。
- 无不可解释的资金差异，月度对账差异不超过 0.5%。
- 售后事件不丢失，利润可按订单和 SKU 重算。
- 灾难恢复演练通过，Owner 能在一个工作台完成每日经营。

## 4. 用户与每日经营任务

首版只需要两个 Actor：`OWNER` 与 `SYSTEM`。Owner 管理凭据、发布流程、审批、暂停和人工修复；System 只能按已发布策略运行。后端预留 operator/approver，界面暂不做完整 RBAC。

卖家的每日任务按优先级排序：

1. 处理资金或履约 blocker：已付款未履约、CJ 下单失败、余额不足、退款/拒付。
2. 处理即将超过承诺时间的订单：缺货、无首扫、物流逾期、地址问题。
3. 完成审批和人工履约待办。
4. 检查 Shopify、CJ、Webhook 的最近成功同步时间和对账差异。
5. 审核候选商品与在售商品健康度。
6. 查看净销售额、预估贡献毛利与已实现贡献毛利。
7. 最后再做竞品、流量和选品分析。

因此默认页仍可叫“问答中心”，首屏主体改为运营行动队列，输入框和分析建议置于其后。

## 5. 核心业务实体

### 5.1 编排与执行

- `Workflow`：可编辑的流程容器。
- `WorkflowVersion`：发布后的不可变版本，保存图、ExecutionPlan、Schema/Skill/Prompt 清单和 hash。
- `WorkflowRun`：某个版本的一次运行。
- `NodeRun`：节点针对某个确定性处理单元的一次执行。
- `NodeAttempt`：NodeRun 的每次尝试，历史不可覆盖。
- `EffectLedger`：所有外部副作用的唯一账本。
- `ExecutionEvent`：append-only 审计与时间线事件。

### 5.2 商品与渠道

- `Product`：商品款式层实体。
- `Variant`：颜色、尺码等真实可售单元。
- `SupplierOffer`：CJ 供应商品、仓库、成本、库存、运费与时效快照。
- `ChannelListing`：Shopify 商品/Variant 的 desired state 与 observed state。
- `MerchantOverride`：标题、价格等人工覆盖，包含生效和到期时间。

唯一性最低要求：`tenant_id + provider + source_product_id + source_variant_id`。Shopify Variant 与 CJ Variant 必须显式映射并记录确认方式和置信度。

### 5.3 订单、履约与财务

- `Order`、`OrderLine`：订单头和逐行状态。
- `ProcurementOrder`：提交给 CJ 的采购/履约单。
- `Fulfillment`、`Shipment`：支持拆单、多包裹和多 tracking。
- `Return`、`Refund`、`Chargeback`、`SupportCase`：售后与客户补救。
- `FinancialEvent`：append-only 财务事件，用于重算预估与已实现贡献毛利。
- `CustomerConsent`：营销同意、退订和 suppression 证据。

### 5.4 人工处理与异常

- `ApprovalRequest`：预期的人工作业授权。
- `IncidentGroup`：同类异常聚合。
- `IncidentOccurrence`：每个订单、SKU、Variant 或节点的独立异常记录。
- `ActionInboxItem`：前端投影，将审批、异常和人工任务显示在同一收件箱中，不改变底层语义。

## 6. 状态模型

### 6.1 工作流与执行

```text
WorkflowVersion: DRAFT -> PUBLISHED -> DEPRECATED
WorkflowRun: QUEUED -> RUNNING <-> WAITING_RETRY / WAITING_APPROVAL / PAUSED
             -> SUCCEEDED / FAILED / CANCELLED
NodeRun: PENDING -> READY -> RUNNING -> SUCCEEDED / SUCCEEDED_WITH_WARNING / SKIPPED
         RUNNING -> RETRY_SCHEDULED -> READY
         RUNNING -> WAITING_APPROVAL -> READY / FAILED
```

所有迁移通过领域命令发生并写入 `ExecutionEvent`。界面不可直接更新状态字段。

### 6.2 外部动作

```text
Effect: PREPARED -> SUBMITTED -> CONFIRMED
        SUBMITTED -> UNKNOWN -> CONFIRMED / FAILED
        CONFIRMED -> COMPENSATION_PENDING -> COMPENSATED / COMPENSATION_FAILED
```

`UNKNOWN` 表示请求可能已在外部成功但响应丢失。此时只允许“查询状态/对账”，禁止手动重试。

### 6.3 审批与异常

```text
Approval: PENDING -> APPROVED / REJECTED / EXPIRED / CANCELLED / SUPERSEDED
IncidentGroup: OPEN -> ACKNOWLEDGED -> MITIGATING -> RESOLVED / AUTO_RECOVERED
```

审批必须绑定 `payload_hash`、工作流版本、节点配置、目标对象、金额和过期时间。批准后任一关键参数变化都使审批失效。

### 6.4 商品、渠道和库存

商品至少拆成四个维度：

- `product_lifecycle`：CANDIDATE / EVALUATING / READY / CONTENT_DRAFTING / PUBLISH_READY / ACTIVE / UNPUBLISHED / ARCHIVED。
- `listing_state`：NOT_CREATED / DRAFT / ACTIVE / HIDDEN / ARCHIVED / ERROR。
- `availability`：UNKNOWN / IN_STOCK / LOW_STOCK / OUT_OF_STOCK / NOT_SERVICEABLE。
- `health`：NORMAL / WARNING / BLOCKER。

例如，一个商品可以同时是 `ACTIVE + ACTIVE + OUT_OF_STOCK + BLOCKER`。看板仅按生命周期分列，其他维度作为徽标和筛选。

### 6.5 订单主路径

```text
NEW -> PAID -> RISK_CHECKED -> READY_TO_PROCURE -> CJ_SUBMITTED
    -> SUPPLIER_PROCESSING -> PARTIALLY_SHIPPED / SHIPPED -> DELIVERED
```

旁路包括 `ON_HOLD`、`PARTIAL_OOS`、`CANCEL_REQUESTED`、`REFUND_PENDING`、`RETURNED`、`CHARGEBACK`。状态必须落到 OrderLine，订单头由行状态投影得出。

## 7. 字段所有权与同步原则

| 数据 | 主事实源 | 本地责任 | 冲突处理 |
|---|---|---|---|
| CJ 规格、成本、库存、仓库、运费 | CJ | 保存带采集时间的只读快照 | 超过 freshness 阈值即禁止高风险动作 |
| 标题、定位、定价策略 | 本地 | 保存生成版本和人工覆盖 | 人工覆盖优先，并有到期策略 |
| Shopify 发布状态与在线实际值 | Shopify | 保存 desired/observed state | 定期 reconcile，漂移生成待办 |
| 订单、折扣、退款 | Shopify/支付渠道 | 增量同步与漏单对账 | Webhook + 定时拉取双通路 |
| 物流轨迹 | CJ/承运商 | 保存事件时间线与 SLA 投影 | API 恢复不自动关闭客户补救任务 |
| 财务结果 | FinancialEvent 账本 | 可重算、可追溯 | 禁止覆盖历史事件 |

所有数值展示必须包含币种、口径和 `as_of`。库存、成本、运费和时效必须有 freshness 阈值。

## 8. 利润口径

`estimated_contribution_margin` 用于选品、上架和下单前判断；`realized_contribution_margin` 用于订单完成后的真实复盘。

最低口径：

```text
净销售额 = 商品金额 - 折扣 - 退款 - 代收代付税费
贡献毛利 = 净销售额
         - CJ 货品成本
         - CJ 运费
         - 支付/平台费
         - 广告获客成本分摊
         - 退货、重发与拒付损失
         - 汇兑损益
```

选品分数不得替代利润计算。LLM 只能解读确定性计算结果。

## 9. 动作策略与风险护栏

用以下策略替代 L0/L1/L2：

- `REVIEW_BEFORE_EXECUTE`：执行前审批。
- `EXECUTE_AND_NOTIFY`：仅在动作支持安全补偿且满足护栏时可用。
- `AUTONOMOUS`：仅适用于通过观察期、影响可控的动作。

每个 ActionType 声明：`allowedPolicies`、`supportsUndo`、`rollbackWindow`、`amountLimit`、`entityCountLimit`、`marginFloor`、`maxDataAge`、`allowedTimeWindow`、`batchSize`、`samplingRate`、`circuitBreaker` 和 `minimumPolicy`。

采购、退款、群发邮件首版固定为 `REVIEW_BEFORE_EXECUTE`。自动化升级不能只看连续 20 次成功；还需最小观察天数、金额覆盖、人工修改率、异常率和补偿成功率。

每个外部动作统一走“计划 → 校验 → 执行 → 核验 → 补偿/人工恢复”。

## 10. 工作流、契约与 Skill

发布工作流时生成不可变 `ExecutionPlan`。发布校验至少包含：无环、必填配置、边契约兼容、凭据可用、预算、动作策略、幂等策略、补偿策略和至少一个触发器。

Skill 首版只允许白名单包，生命周期为 `ACTIVE / DISABLED / DEPRECATED`。被已发布版本引用的 Skill 不可物理删除。

Skill manifest 至少声明：输入输出 Schema、side effect、幂等、重试、超时、供应商限流、审批、补偿、凭据、成本估算和 PII 策略。

Contract Registry 冻结 `schema_hash`。金额统一使用 decimal string + currency，时间统一 UTC ISO8601，并明确 optional/null、单位、枚举扩展和 PII 分类。Zod 与 Pydantic 从同一 JSON Schema 生成或用一致性测试约束。

## 11. 异常、审批和行动收件箱

异常聚合 fingerprint 至少包含 tenant、workflow version、immutable node key、类别、标准化错误码、credential/vendor 和可选影响范围。一个 Group 下保留全部 Occurrence，支持逐单查看、重试和关闭。

默认首页的行动队列排序：

1. 资金/履约 blocker。
2. 即将超 SLA 的订单与客户承诺。
3. 待审批。
4. 数据不同步或 freshness 过期。
5. warning 与运营洞察。

凭据问题的标准动作是重新授权、查询影响范围、按 occurrence 恢复。通用的“手动重试/暂停流程”不足以处理缺货、地址、退款、换仓和客户沟通，详情页应按错误类型提供对应动作。

## 12. 信息架构

```text
问答与行动中心（默认首页）
商品
订单与履约
流程
需要处理（异常 / 审批 / 人工任务）
模板
管理（客户 / 竞品）
设置与凭据
```

顶栏显示“阻塞异常、待审批、最老待处理时长、同步健康、LLM 成本”。全绿时可收起，存在 blocker 时不可折叠。

Cmd+K 为 P0，至少支持 SKU/标题、Run ID、Incident ID、Shopify Order ID。面包屑按“对象类型 → 对象”展示。

流程画布首版采用 React Flow controlled 模式，只支持内置模板 fork、参数编辑、可选节点开关和只读运行视图。自由连线、运行时安装任意 Skill 和完整模板市场后置。

问答采用紧凑时间流，异常与结果展开为结构化卡。今日概览、异常卡和审批在 LLM 不可用时仍必须工作。

## 13. 问答边界

首版限定意图：今日待办、昨日净销售与预估毛利、某商品为何失败/下架、某订单在哪里、某异常影响哪些对象。每个数字显示数据源、计算口径和时间。

LLM 不直接执行 SQL、不直接写业务表、不自行计算金额。写操作只能生成 command draft，用户看到目标、diff、影响范围、最坏结果和可补偿方式后，由统一命令 API 执行或发起审批。

## 14. 成本、安全与可靠性规则

- LLM 预算在调用前原子预占，完成后按实际费用结算。
- 预算耗尽只阻止新 LLM 调用或新 Run，不得阻断无需新增成本的履约收尾、补偿和告警。
- Inngest 是调度、重试与等待的唯一任务真相源；Redis 只做供应商级限流、并发信号量和短期缓存。
- 凭据只保存 secret reference，不进入 Plan、事件、日志或 Prompt。
- Webhook 校验签名、时间窗并按 event ID 去重；数据库写入与 outbox 同事务。
- 原始大 Payload 使用加密对象引用和 hash；数据库保存可展示摘要。执行回放默认脱敏。
- 暂停表示“不再调度新节点”；取消在途动作只能尽力而为，界面必须说明实际状态。

## 15. 验收场景

1. 同一触发事件投递 100 次只创建一个 Run；上架节点崩溃重启后 Shopify 仅有一个商品。
2. 供应商成功但响应超时，Effect 进入 UNKNOWN；对账确认后转为 CONFIRMED，期间不重复调用。
3. 同一错误 47 次显示一个 Group 和 47 个 Occurrence，每个订单可独立处理。
4. 审批后修改 SKU、价格或配置，执行因 payload hash 不一致被拒绝。
5. M/Black 无唯一 CJ Variant 映射时，在扣款或发布前拦截并要求人工确认。
6. 商品已发布但某 Variant 缺货时，商品生命周期不变化，availability 与 health 正确变化。
7. 付款后 CJ 缺货，订单进入 PARTIAL_OOS，并给出换仓、换款、退款和联系客户等操作；库存恢复不自动代表订单已解决。
8. 一单三件来自两个包裹时，逐行和逐包裹状态正确，不能提前标记全量履约。
9. Webhook 丢失时，定时对账发现订单数量或金额差异并补拉。
10. LLM 不可用时，行动队列、确定性指标、审批和异常处理仍可用。
11. 预算耗尽时停止新 LLM 调用，已付款订单的履约、告警和补偿继续。
12. 凭据失效只影响依赖该凭据的动作，重新授权后按 occurrence 和幂等账本恢复。
