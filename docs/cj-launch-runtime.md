# CJ 选品到测试站：十五步真实执行

## 已实现范围

保留原十五个节点，在同一个 WorkflowRun 中依次执行。设计器保存到后端，DesignRelease 锁定完整设计、Skill 版本、店铺版本与摘要；工具栏启动读取冻结版本，不另开画布、不重新填写参数。历史七步发布版本仍按原图执行。

真实支持 US/USD、test-store、供应商履约设计。只读 CJ 采集与报价；不会创建 CJ 采购单、付款、发邮件或启动广告。历史冻结版本仍按原单商品规则执行；新 CJ v4 批次按合格商品目标补位并逐款发布，详见下方批次章节。

## 节点与输入

- 商品任务：CJ 类目、各类关键词、空结果策略；新批次合格目标 1–100 款、每商品研究规格 1–20 个。
- CJ 采集：继承任务，持久化查询记录；空结果停止，不擅自扩大范围。
- 资料检查：分商品读取详情，校对商品标识、规格与未研究数量。
- 库存筛选：分规格读取库存，校对商品/规格关系，优先已验证 CJ 仓现货。允许工厂供货须明确备货天数与限售量，单独标记，不冒充已验证库存。
- 配送核验：用实际供货仓库国家和任务销售国家试算线路，逐规格记录运费、税费、时效和原始报价时间。
- 策略：明确选择已注册的 `product.opportunity@1.0.0`，按成本、时效、库存缓冲评分并建议售价，算法见 `opportunity-skill.md`。旧 `product.decision.landed-cost@1.0.0` 保留历史成本优先排序。二者均为确定性规则，不是 LLM，不预测销量，不自动替换配置。
- 核算：继承费用率、目标贡献率和明确税费预留，产出售价建议与广告前贡献。缺税费不当零，报价有效期不因后续步骤延长。
- 商品审核：绑定本轮商品事实、选品证据、版本与摘要；工厂供货强制人工确认。
- 内容：仅已审核注册的 `content.editorial.v1`，沿用原素材与事实，不执行上传脚本或假装生成素材。
- 渠道检查、最终审核：复用受信测试站适配器和原审批逻辑。
- 准备发布：检查批准、必填字段、冻结店铺、安装包与摘要，持久化 PreparedPublication。日常执行使用已安装代码，不调用模型猜值。
- 发送：重新核对准备结果与批准商品完全一致，使用既有幂等操作和超时查询策略。
- 可售核验与归档：查询真实测试站数据，核对商品、店铺、摘要及完整内容，才写入 ChannelListing 并同步商品模块。

## 执行边界

`registry/launch.py` 是闭合运行策略校验，`runtime/launch.py` 是七个前段节点的受信处理器；审批和发布复用 `runtime/services.py`，索引按实际节点职责定位，不硬编码七步位置。每批外部调用后持久化进度并重新领取，未完成的同一节点不传递到下游。

SelectionTask 使用 `workflow_owned` 状态归属于该运行，独立选品 worker 不领取它。运行与独立选品共享团队配额保护。失败保留进度并释放选品占用，恢复检查其他执行中任务；取消不撤销已经发生的渠道发布。

内部阶段数据是受信执行器的运行结构；不能宣称前端所有 v2 Schema 已形成任意 DAG 后端。前向主线必须完整；协作连线是可选证据关系声明，不自动启动旁路，返工使用受控修订 API。通用并行 DAG、任意协作执行、自建模型/生图运行器、其他渠道仍未实现。冻结不会自动替换未部署的 Skill 或改写用户参数。

## 验证

`backend/tests/test_launch_workflow.py` 使用模拟 CJ 回包、临时数据库和实际测试站 DRF API，覆盖十五节点、两轮批准、多规格分批、准备结果篡改、无结果停止及本机免审核审计。

`scripts/test-launch-browser.cjs` 拦截所有业务请求，验证当前画布启动、无重复配置、没有商品输入替代 CJ 任务、两轮审核和结果展示。它不创建用户商品，不替代真实 CJ 接入验收。
# 合格商品发布批次（已实现受信测试站主线）

## 集中配置的十三步新主线

当前运营模板为十一节点：任务配置（含已注册选品/定价策略） → 完整数据采集 → 统一核验、定价并补选 → 第一轮审核 → 内容制作 → 渠道检查 → 最终审核 → 准备发布 → 提交发布 → 可售确认 → 完成。

`selectionStrategy` 保存任务使用的策略版本与参数；排序、售价建议及独立售价复核是统一节点内部阶段，不再分成运营节点。完整证据及两轮审批保留。历史十三步、十五步冻结图照原样执行；新图实际连线先检查，内部兼容校验不写回冻结图。十一节点回归覆盖补选、补查、短缺暂停、恢复及批次发布，不表示其他渠道已接入。

库存、工厂供货、最长总时效及费用条件只在任务配置。统一节点内部保留资料、库存及配送核验断点；缺额继续补位，不把局部通过当整体合格，明显不合格不查无用运费。策略执行后系统独立复核售价，沿用原费用配置、不重新设置。`runtime/unified_selection.py` 负责新节点，原十五步执行器保持历史兼容；子运行起点按定义查找，不依赖旧节点位置。标准编辑草稿升级保留实际数值和绑定，需要保存并重新冻结；不修改已有运行、审批或定时计划绑定。

“选20款”表示完成资料、库存、配送、成本与系统核算的20款不同CJ商品，经两轮审核后逐款发布，而非20个原始样本或20个SKU。新编辑草稿绑定 CJ v4 时写入 demandFirstCollection 与 batchPublishing；服务端冻结出 batch_target。没有该标志的历史冻结版本保持原单商品行为。实现位于 runtime/batch.py，同一运营画布内补位研究；内部子运行负责逐商品幂等、准备、发布与可售核验，不生成另一套用户画布。

已用模拟 CJ 回包、临时数据库及实际测试站 DRF 接口验证补位、多规格合并、缺额暂停、两轮批次批准、商品投影与部分失败仅重试失败成员。这不是本次实际采集并上架20件用户商品，其他渠道与生产多 worker 并发尚未验收。

## 数量与研究策略

需求前置采集现在复用 CJ 完整详情中的 `stanProducts` / `variantInventory`：一次请求保存订单证据、必要商品资料、规格价格与库存来源的精简快照。批次的资料检查和完整快照规格筛选在同一 worker 回合完成，两个节点分别留下执行记录。资料/规格字段不足才补查原详情接口；空库存、零库存仍按原规则排除，过期快照不续期，工厂报量不当作 CJ 现货。搜索分页与运费仍是独立请求。此优化不是任意 DAG 并发执行器，也没有启用 SQLite 多 worker 写入。

- 新建 CJ v4 草稿以 `demandQualifiedQuota=true` 将 `scanBudget` 改为订单达标候选额度（默认1000，可调20–10000）。低订单、未知订单、重复及检查时已上架商品不占额度；继续分页至额度达到、目录结束、完整重复页或1000页安全边界。实际读取量与达标数分开持久化展示；此额度不保证库存/配送通过。旧冻结运行缺开关仍按原始扫描预算，不迁移。
- 在用户原有类目/关键词范围内分页，先排除同店铺已上架/提交待确认商品；未知需求及低于门槛者立即淘汰，不继续读取规格或运费。当前已实现的CJ需求证据是周期未声明的orderCount，不得叫作90天销量。
- 单关键词批次逐页研究需求达标商品，持续翻页直到目录结束或扫描预算用尽，不因凑够目标数量停止。只有可履约规格才查运费，最后对全部合格候选统一执行已注册策略并独立核算价格。保存每一步事实和排除原因，不重新请求已淘汰商品，不刷新证据时间伪装新查询。
- 一款商品至少有一个经过完整检查的合格规格才占一个商品名额；多个合格SKU仍算一款，未研究SKU不发布。研究规格上限不能解释为单商品规格全部可售。
- 研究范围用尽后按每商品最高合格规格的策略排名选前 N 款；同商品多规格不重复占名额，多类目保留原配额。数量不足则暂停，不自动减量或扩大类目。合格数与最终选取数分别记录，只有最终清单进入两轮审批及逐款发布。
- 评分范围是本次扫描预算/搜索范围及规格研究上限内，不承诺全目录最优。全范围研究会增加只读请求与等待；保持原限频和一小时证据有效期，过期暂停，不伪造时间。冻结参数不改写，已完成审批清单不重新选择。

## 批次与逐商品执行边界

- 父批次保存不可变配置/合格商品清单摘要、真实研究进度、两轮批量审核和整体结果；每款成员有唯一CJ PID、完整合格SKU简报、内容摘要、映射结果和独立发布/可售证据。
- 保持一个运营画布，节点展示目标/合格/成功/待确认/失败计数；商品明细在当前画布面板展开，不要求逐款建立画布或重复配置接口包。
- 第一轮确认所有商品、SKU、售价及履约事实；第二轮确认逐商品最终内容和发布请求。一次批量批准必须绑定成员清单及每成员摘要，不能复制人工决定伪装为逐款审批。任何内容、成员、适配代码或连接版本变化必须重新检查并按影响范围审核。
- 复用已审核内容和渠道执行代码，但不能用一条旧ChannelListing记录装下20款商品；需要父批次与逐商品结果关系。服务端验证批量批准对成员的确切覆盖，前端勾选不构成授权。
- 发布采用逐款独立幂等键并处理回执。18款成功、2款失败/未知时保留18款结果，仅处理那2款；未知结果先查询再用原键重试。不回滚或重复发布成功商品，也不把ACCEPTED当作可售。
- 筛选通过是证据时点的事实，不保证外部平台必然接受、库存永不变化或人工必然批准；发送前按有效期与真实店铺状态复核，失效商品单独暂停，不为凑数放宽校验。

## 不为动画消耗业务时间

- 后端只等待CJ限频、必要的请求/退避、真实事件或人工审批；节点动画及连线传输不控制worker推进。前端按持久化进度展示，事件过多时合并历史动画，不按历史动画队列延迟当前状态。
- 复用受信数据及一小时内有效证据；接口失败不重新开始整个批次。并发仅按供应商配额与数据库能力设置，不按电脑核数无条件加worker，SQLite本地验收不能冒充MySQL/生产并发验收。
- 验收必须覆盖：低需求不查库存、库存不合格不查运费、淘汰后补足目标、短批次明确暂停、多SKU只算一款、批量审批摘要、逐款幂等、部分失败仅重试失败成员、已上架排除、旧运行兼容。不得以20款模拟数据代替真实接口结果。
